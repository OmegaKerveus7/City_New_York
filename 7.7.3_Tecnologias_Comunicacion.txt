 4. TECNOLOGIAS QUE NO SE USAN (deuda tecnica declarada)
--------------------------------------------------------------------------------

 AUSENTE                        CONSECUENCIA / JUSTIFICACION
 -----------------------------  -----------------------------------------------
 WebSocket / SignalR / SSE      No hay push: la UI se actualiza con polling
                                REST. Latencia minima aproximada de 5 s.
 MQTT / AMQP / Kafka / Rabbit   La cola es una tabla SQL. Sirve para 1
                                dispositivo, no escala a muchos.
 gRPC / Protobuf                Todo es JSON en texto; mas consumo pero legible
                                en el monitor serie.
 Modbus / CAN / RS-485          Se eligio I2C por simplicidad de cableado en
                                maqueta.
 BLE / LoRa / Zigbee            Wi-Fi directo a la red local.
 OAuth 2.0 / IdentityServer     JWT propio con clave simetrica; no hay refresh
                                token.
 TLS validado en el ESP32       No se fija CA ni se usa setInsecure() explicito;
                                la validacion depende del core. Riesgo al
                                actualizar el framework.
 HTTPS forzado en el frontend   http.ts apunta a http://localhost:5238; el TLS
                                solo existe en el tramo ngrok.


--------------------------------------------------------------------------------
 5. LECTURA CRITICA (para la defensa)
--------------------------------------------------------------------------------

 - Latencia real del lazo: peor caso = 5 s de polling + 3.5 s de espera de
   respuesta, aproximadamente 8.5 s antes de saber si el comando se ejecuto.
   Promedio aproximado de 2.5 s. A eso se suma el tiempo mecanico (el
   teleferico a 5 RPM tarda mucho mas que la comunicacion).

 - El ESP32 es el unico punto de fallo de red. Si se cae, el sistema queda
   aislado aunque Mega y esclavos sigan vivos. El servidor HTTP local del
   ESP32 solo sirve para diagnostico, no es una ruta alternativa.

 - Seguridad: CORS abierto, contrasena SA en texto plano y
   TrustServerCertificate=True son aceptables en desarrollo, pero deben
   declararse como deuda tecnica y no como diseno final.

 - Coherencia del protocolo: el mismo esquema de texto ASCII atraviesa UART
   e I2C (SERVO_SUBIR viaja sin traduccion). Simplifica la depuracion, pero
   acopla el esclavo a la API: renombrar una instruccion en la BD obliga a
   reflashear los Arduinos.

--------------------------------------------------------------------------------
 7. GLOSARIO BREVE
--------------------------------------------------------------------------------

 TDS      Tabular Data Stream: protocolo propietario de SQL Server.
 JWT      JSON Web Token: credencial firmada que viaja en el header.
 HS256    HMAC con SHA-256: algoritmo de firma simetrica del token.
 I2C/TWI  Bus de 2 hilos (SDA/SCL) con maestro y esclavos direccionables.
 UART     Puerto serie asincrono punto a punto (TX/RX + GND).
 8N1      8 bits de datos, sin paridad, 1 bit de parada.
 Polling  Consulta periodica del cliente al servidor (no hay push).
 TTL      Nivel logico transistor-transistor; 5 V en Arduino, 3.3 V en ESP32.
